# 线上海龟汤聊天室 MVP 设计

日期：2026-06-22

## 背景

目标是做一个“线上海龟汤聊天室”：用户可以从题库选一道海龟汤，创建房间，邀请好友一起通过聊天向 AI 主持人提问，并用卷宗记录线索。

参考来源：

- `work/LABYRINTH`：轻量原生 Web 海龟汤项目，提供 AI 生成、AI 裁判、多人房间、Supabase 实时同步、关键词气泡等参考。
- `https://haiguitang.net/`：成熟的在线海龟汤站点，提供题库、筛选、题卡、游戏房间、AI 主持、游戏聊天、调查卷宗、社区动态、任务与会员等参考。

## 产品定位

初版聚焦“题库驱动的多人 AI 海龟汤聊天室”，不做大而全社区。

一句话描述：

> 选一道汤，开一个房间，邀请朋友在同一个聊天室里向 AI 主持人追问真相。

## MVP 范围

### 必做

- 题库首页：搜索、难度筛选、标签筛选、热门/最新排序。
- 题卡：标题、难度、汤面摘要、标签、作者、评分、游玩人数。
- 题目详情：完整汤面、开始游戏、收藏/举报入口、评分展示、相似题推荐。
- 游戏房间：题面、主持问答、玩家聊天、在线用户、剩余提问次数。
- AI 主持：回答“是 / 不是 / 无关 / 部分相关”，支持最终猜谜判定。
- 调查卷宗：收藏关键问答、私人笔记、已发现线索。
- 多人协作：房间链接邀请，游客昵称加入，最多 10 人。
- 后端 AI 代理：模型密钥只放服务端，前端不保存 API Key。

### 暂不做

- 好友系统。
- 站内信。
- 积分与会员计费。
- 排行榜。
- 任务系统。
- App 下载页。
- 通灵召唤。
- 现场搜证。
- 完整后台运营系统。

这些可以作为视觉入口或后续菜单保留，但初版不实现业务闭环。

## 用户流程

### 选题流程

1. 用户进入首页。
2. 使用搜索、难度、标签筛选题目。
3. 点击题卡进入详情。
4. 阅读汤面与统计信息。
5. 点击“开始游戏”创建私人房间。

### 房间流程

1. 系统创建房间并生成分享链接。
2. 房主进入游戏房间。
3. 好友打开链接，输入昵称加入。
4. 玩家在“游戏聊天”里自由讨论。
5. 玩家在“主持人问答”输入问题，AI 主持回答。
6. 关键问答可收藏到“调查卷宗”。
7. 玩家提交最终推理，AI 判断是否通关。

## 页面结构

### 首页

风格参考 `haiguitang.net`：

- 顶部导航：品牌、今日活跃、随机一题、快速加入。
- 搜索栏：搜索谜题或作者。
- 筛选区：专题、难度、标签、热门/最新。
- 题库列表：紧凑题卡网格或列表。
- 右侧栏：茶水间/公告/最近动态可以作为后续占位。

### 题目详情页

- 返回按钮。
- 标题、难度、标签、作者。
- 汤面正文。
- 评分、游玩人数、通关率、平均提问、平均耗时。
- 开始游戏按钮。
- 相似题推荐。

### 游戏房间页

参考 `haiguitang.net` 的三栏布局：

- 左侧：题面、标签、作者、房间状态、剩余提问。
- 中间：主持人问答记录，输入框，最终猜谜入口。
- 右侧：在线用户、玩家聊天、调查卷宗入口。
- 底部：移动端输入区固定在底部。

## 视觉方向

整体风格采用“深色侦探工作台”：

- 背景：深蓝灰、低对比网格或暗纹。
- 卡片：8px 半径以内，细边框，弱阴影。
- 文本：高可读中文排版，题面正文行高更宽。
- 重点色：蓝色用于主操作，橙色用于现场/验证类动作，绿色用于连接状态。
- 标签：胶囊标签，难度用简单/中等/困难三色区分。
- 信息密度：偏工具型，不做营销式大 Hero。

`LABYRINTH` 的玻璃感和 AI 思考动画可少量保留，但不要让界面变成过度装饰。

## 技术方案

推荐初版使用：

- 前端：React + Vite + TypeScript。
- 实时通信：Socket.IO。
- 后端：Express + TypeScript。
- AI 代理：服务端调用 OpenAI-compatible Chat Completions API。
- 数据：初版使用内置 seed 题库和内存房间；上线前替换为 Postgres/Supabase。
- 测试：Vitest 覆盖题库筛选、房间状态、AI 回答解析。

选择 Socket.IO 而不是直接复刻 `LABYRINTH` 的前端 Supabase 调用，是为了避免把 API Key 或敏感配置暴露给浏览器。后续如果需要托管数据库和订阅能力，可以把房间服务替换为 Supabase Realtime。

## AI 主持规则

系统提示应约束模型：

- 只基于汤底和已知上下文回答。
- 普通提问只能回答“是 / 不是 / 无关 / 部分相关”，可补充一句很短的主持人提示。
- 不直接泄露汤底。
- 玩家提交最终推理时，给出通过/未通过判断和缺失要点。
- 回答必须返回结构化 JSON，后端负责解析和兜底。

## 错误处理

- AI 服务超时：显示“汤仙人正在走神，请重试”并允许重试。
- 模型返回非 JSON：后端降级为 `partial`，保留原文摘要。
- 房间满员：提示最多 10 人，禁止加入。
- 房间不存在：进入“房间已失效”页面。
- 网络断开：顶部显示连接状态，重连后拉取最新房间状态。

## 测试策略

- 题库筛选：搜索、难度、标签、排序。
- 房间状态：创建房间、加入、离开、满员、提问计数、通关。
- AI 解析：合法 JSON、非 JSON、超时、失败返回。
- UI 冒烟：首页能显示题卡，题目详情能开始游戏，房间能发送聊天和主持问题。

## 已知风险

- AI 裁判稳定性会影响核心体验，需要结构化输出和回退逻辑。
- 海龟汤题库版权要谨慎，初版应使用自建、授权或原创 seed 题。
- 房间状态如果只放内存，服务重启会丢失；上线前需要持久化。
- 多人并发提问需要做节流和主持人队列，否则 AI 成本和状态一致性会失控。
